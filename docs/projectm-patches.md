# projectM patch log

Constitution VIII (v1.1.0, amended 2026-11-09): `Vendor/projectM` may be pinned to the project
owner's fork only when the pinned commit is an upstream commit plus the patches listed here, each
proposed upstream. Nothing else goes on the fork branch.

| 2 | `49c5005` | `GLResolver`: when a user resolver is supplied and `Initialize()` cannot probe a current context, the resolver state records that the application manages the context, and `VerifyBeforeUse()` trusts it instead of re-probing. | On iOS the context is EAGL, which none of the probed backends (EGL, CGL, ...) can see. `Initialize()` already proceeded on that assumption, but `VerifyBeforeUse()` re-probed EGL and refused, so `projectm_create_with_opengl_load_proc()` always returned NULL ("Context for detected backend is not available (backend=EGL)"). Found by `PMEngineTests` (T068). | Proposed in projectM-visualizer/projectm#1075 (open, 2026-11-10), from `Coastrnaut/projectm:ios`. |

| 3 | `ca1fc0d` | `GLResolver`: on Apple's embedded platforms (iOS, iPadOS, tvOS, watchOS, visionOS), a user resolver is authoritative. `Initialize()` opens no native libraries and `ResolveProcAddress()` returns the user resolver's result with no provider, global (`dlsym(RTLD_DEFAULT)`) or library fallback. | RI-009 (ADR-0003): with our load proc supplied, the engine still tried to `dlopen` eleven EGL/GLES names (`@rpath/libEGL.dylib` … `libGLESv2_with_capture.dylib`) that never exist on iOS, seen on D2 (iPadOS 27.2) with RendererLab 2026-11-09, and fell back to global `dlsym` lookups. The fix keeps every GL lookup inside the application's resolver. | Proposed in projectM-visualizer/projectm#1075 (open, 2026-11-10), from `Coastrnaut/projectm:ios`. |
| 4 | `c88894e` | Fixes to patches 1 and 3 (owner's commit): `GLResolver.cpp` included `<TargetConditionals.h>` inside the `_WIN32` block, so `TARGET_OS_IPHONE`, and with it `IsAppleEmbeddedPlatform()`, depended on another header defining it; the include now sits in the `__APPLE__` path. Adds a fork CI job that builds the iOS, iOS-simulator and tvOS frameworks, checks bundle layout, Info.plist and install names, and links a client. | Makes patch 3 independent of include order and completes patch 1 for the playlist library (which this app does not build). | Proposed in projectM-visualizer/projectm#1075 (open, 2026-11-10), from `Coastrnaut/projectm:ios`. |
| 5 | `e5b77ab` | Custom shapes (fill and outline), the darken centre and looped waveforms (circle and the two 2077 loop modes) no longer use `GL_TRIANGLE_FAN` or `GL_LINE_LOOP`. New `VertexIndexArray::MakeTriangleFanAsTriangles()` builds the fan's triangle list (`0, i, i + 1` per triangle) and `MakeLineLoopAsLineStrip()` the closed strip (`0 … n-1, 0`) on the CPU; the meshes draw them as `Triangles` and `LineStrip`, uploaded with the existing `glBufferData`/`glBufferSubData` path. The same triangles and segments are rasterized; `Mesh::PrimitiveType::TriangleFan` and `LineLoop` stay for API compatibility. | QA-011 device run 2026-11-19: the app's main thread hung for good when the app went to the background while a preset with custom shapes drew (SIGABRT spindumps on D2 and D3: `CustomShape::Draw` → `Mesh::Draw` → `GL_DrawElements(GL_TRIANGLE_FAN)` → `ContextMtl::drawTriFanElements` → `generateTriFanBufferFromElementsArrayCPU` → `mtl::Buffer::mapWithOpt` → `-[MTLCommandBuffer waitUntilCompleted]`). Metal has no fans or loops; ANGLE's Metal backend on Apple GPUs (`hasCheapRenderPass` off) rewrites the indices on the CPU into a pooled scratch buffer for every such draw and maps it with a GPU sync, so once the frame's command buffer references that buffer each fan or loop draw commits and waits for the GPU: in the foreground a CPU/GPU round trip per shape, and a wait that never ends once iOS stops running the app's GPU work. Byte-identical output on the iOS 27.2 simulator (`CustomShapeDrawTests`, old and new engine). | Not yet proposed; upstream-ready (no iOS-specific code). |
