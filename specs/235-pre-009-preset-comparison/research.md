# Research: PRE-009 Preset Comparison

- **PRE-009-D1 Where the shared PCM comes from.** Decision: the renderer's attached reader (`NormalizedPCMRing` behind AUD-013's delay), read on the main thread by the comparison's tick driver while the main visual is paused. Rationale: the ring is single-consumer; the renderer already reads it on the main thread, so the consumer thread never changes. Alternatives: reading on the worker thread (breaks SPSC if the renderer resumes), a tap copying the renderer's reads (needs the main visual running at 60 fps, the GPU cost we want to avoid).
- **PRE-009-D2 Lockstep by construction.** Decision: one worker thread draws both engines for every batch (A then B), each engine on its own unshared context made current in turn. Rationale: two threads would need a barrier and could still let one engine see a batch the other has not; one thread makes drift impossible. Alternative: one thread per engine with a shared barrier (more code, same result at best).
- **PRE-009-D3 Slow previews.** Decision: a mailbox of ticks; the worker takes all waiting ticks at once and joins them into one batch (samples concatenated in order, the last tick's frame time); over 6 waiting ticks the oldest are dropped before anyone sees them and counted. Rationale: both engines then skip display frames together and catch up together; audio stays continuous within the kept window. Alternatives: an unbounded queue (latency grows without bound), dropping the newest (stale audio).
- **PRE-009-D4 Frame time.** Decision: tick n carries n / rate seconds; the batch passes its last tick's frame time to `setFrameTime` on both engines (PRE-005's pinned clock). Rationale: the two engines' `time`-driven motion is identical, and pixel-identical frames for the same preset are testable.
- **PRE-009-D5 Feeding the engine.** Decision: a batch's samples go to each engine in chunks of at most `maxSamplesPerFrame` frames, the same chunks for both. The instrument records one delivery per engine per drawn batch: first and last tick, frame time, first sample, sample count and an FNV-1a checksum of the sample bits, captured right before that engine is fed.
- **PRE-009-D6 Safety.** Decision: each preview draws through its own `PMFlashLimiter` (created on its context) into the read-back target with `FlashEnvelopeConfiguration.limiterParameters(frameTime: batch duration)`, using the clamp given at session start (`flashLimitsOverride ?? forReduceFlashing(reducesFlashing)`).
- **PRE-009-D7 Display.** Decision: RGBA read-back (top row first, as PRE-001) converted to a `UIImage` on the main actor per frame pair; 320 × 180 × 4 × 2 = 460 KB per batch. Alternative: two CAMetalLayer window surfaces (zero copy, but a second presentation path and layer lifecycle in SwiftUI; not worth it at this size).
- **PRE-009-D8 Main visual.** Decision: paused while the sheet is open (`renderer.pause()`), restored by `resumeActiveVisual()` on close. Rationale: sheet covers it; budget goes to the previews; the comparison is the reader's only consumer in practice.
- **PRE-009-D9 Silence.** Decision: a tick whose read returned 0 frames carries 1 470 frames (one 30 fps tick at 44.1 kHz; 2 940 at 15 fps) of PRE-001's deterministic thumbnail signal, continued across ticks; the sheet says "No audio playing: showing a test signal".
- **PRE-009-D10 Lifecycle.** Decision: `stop()` asks the worker to end and waits briefly (as `setSuspended`); PERF-011 suspension and PERF-006 memory pressure stop it; engines, contexts and targets exist only during a session.
