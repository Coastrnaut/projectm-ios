# Research: UIX-006 Touch Gesture Mapping

- **UIX-006-D1 Recognition: one custom recogniser plus a pure classifier.** Separate UIKit recognisers (two `UITapGestureRecognizer`s, four `UISwipeGestureRecognizer`s) each fire on their own, and their mutual exclusion would live in `require(toFail:)` wiring that cannot be unit-tested and that SwiftUI's representable API (one recogniser per representable) cannot express. One `UIGestureRecognizer` subclass instead records, per touch sequence, the most fingers down at once, each finger's displacement and the duration, and hands a `GestureTouchSummary` to the pure classifier and resolver. Precedence is then one tested function. Rejected: six UIKit recognisers.
- **UIX-006-D2 Thresholds.** Tap: every finger moves ≤ 20 pt and the sequence lasts ≤ 0.5 s (UIKit's tap allowable movement is of the same order). Swipe: exactly two fingers, average displacement ≥ 50 pt along the dominant axis (the other axis smaller), within 1.0 s. Between 20 and 50 pt nothing is recognised (a deliberate dead band so a sloppy tap never becomes a swipe). Three fingers: tap only (three-finger swipes are iOS undo/redo). Four or more: nothing.
- **UIX-006-D3 Coexistence with the one-finger tap.** The recogniser is attached with `UIGestureRecognizerRepresentable` (iOS 18+). It overrides `shouldBeRequiredToFail(by:)` to return true for the other recognisers on the same touch, so the controls' tap (and CAM-005's double-tap) waits for it to fail. It fails as soon as a sequence cannot become a mapped shortcut: when a one-finger sequence ends, when one finger moves beyond the tap slop, when the duration passes 1 s, or when a fourth finger lands. A one-finger tap therefore fails it at touch-up, which is when the single tap would recognise anyway: no added delay (R11). When an action wins, the recogniser ends (recognised) and the single tap is cancelled: one action per touch.
- **UIX-006-D4 VoiceOver.** While `UIAccessibility.isVoiceOverRunning`, VoiceOver consumes multi-finger touches itself; the app also does not attach the recogniser (observed through `UIAccessibility.voiceOverStatusDidChangeNotification`) and the resolver returns nil when told VoiceOver runs, so even an injected recognised set fires nothing.
- **UIX-006-D5 Actions.** Next/previous cue call `show.next()/previous()` (the keyboard's quiet path, SHOW-001). Next/previous preset run `presets.next()/previous()` inside `announcingPresetChange` (ACC-004 preset announcement) without `showControls()`. Tap tempo calls `tempo.tap()` (SHOW-011) without revealing the controls. Show/hide HUD toggles `sceneHUD.isEnabled` (UIX-013).
- **UIX-006-D6 Storage.** One key holding a JSON string `{"enabled":…,"mapping":{gesture: action}}` keeps the switch and the six choices atomic and adds one entry to every key list. Absent → off with the default mapping. Decoding ignores unknown gesture or action names.
- **UIX-006-D7 Lock.** `GestureShortcutsSetting` writes only through `setEnabled(_:)` and `setAction(_:for:)`, each first asking `SceneLock.refusesEdit()`; the settings section is `.disabled(lock.isLocked)` and shows the lock note. The performer path (`performGestureShortcut`) never consults the lock.
