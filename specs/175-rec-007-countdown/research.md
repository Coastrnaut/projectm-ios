# Research: REC-007 Recording countdown

- **REC-007-D1 Where the countdown lives.** Decision: in `VideoRecordingCoordinator` as state `.countingDown(remaining:)`. Rationale: the Record toggle, the refusals, the context check and the background observer already live there, so cancellation and "starts once" are decided in one place. Alternatives: a separate countdown coordinator in front of Record (two state machines to keep consistent; the indicator and external-display hold read one state).
- **REC-007-D2 Time source.** Decision: an injected `RecordingCountdownClock` with `now` (seconds) and `schedule(at:_:)` returning a cancellable token; the system clock uses `ProcessInfo.systemUptime` and a main-actor `Task.sleep`. Ticks are scheduled at `start + k` (k = 1…n), so the count never drifts. Tests use a manual clock that fires due actions as it is advanced. Alternatives: `Timer` (not injectable), `Task.sleep(1 s)` loops (drift, wall-clock tests).
- **REC-007-D3 Exactly once.** Decision: a generation number increments at every begin and cancel; a tick acts only when its generation matches and the state is still counting; completion sets the generation forward before it calls the start path. Rationale: a stale or duplicated callback, or a late tap, cannot start a second recording.
- **REC-007-D4 Late taps.** Decision: Record taps within 0.25 s before completion or 0.5 s after the start the countdown caused are ignored (both measured on the countdown clock). Rationale: a tap meant as "cancel" arriving at the last instant would otherwise race the start, and a tap a moment after it would stop a recording the user just waited for; the acceptance names a tap at 2.99 s and at 3.0 s. The Cancel button and Escape are explicit and are not guarded.
- **REC-007-D5 Refusals.** Decision: `RecordingGate` and the offered-result check run at the Record tap (no countdown when refused) and the full start path runs again at completion. Storage (REC-015) is read only at completion: nothing is read or written before.
- **REC-007-D6 Automatic cancellation.** Decision: the existing 0.25 s context check also runs during a countdown and cancels on visualizer left (no visual shown), visual changed or lost, stopped frame loop, blackout and Pause; `didEnterBackground` cancels. Rationale: same rules as a running recording's stops, so a countdown never completes into an immediate stop.
- **REC-007-D7 Announcements.** Decision: rows X9d ("Recording in 3", then "2", "1"; cause user) and X9e ("Countdown cancelled" user, or "Countdown cancelled: <reason>." system; presentation caption) on the `recording` lane via `StatusEventRouter`. One second apart, they pass the lane's 1 s window. X9 "Recording started" follows at completion as today.
- **REC-007-D8 Motion.** Decision: the number is plain text with no animation and no transition at all, so Reduce Motion needs no special case and `check_motion_policy.py` has nothing to flag.
- **REC-007-D9 Escape.** Decision: the overlay's Cancel button carries `.keyboardShortcut(.cancelAction)`, which SwiftUI binds to Escape on a hardware keyboard.
- **REC-007-D10 Other triggers.** Audit: only `ControlsOverlay`'s Record item calls `toggle()`; OSC and MIDI (MIDI-008 transport included) have no recording action. Nothing else needs a guard.
- **REC-007-D11 Backup.** Decision: the key is a preference: in FILE-005 `includedKeys` (erased with Settings by derivation), in `ALLOWED_KEYS`, removed by `-uitestResetNotice`.
