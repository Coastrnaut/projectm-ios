# Research: SCN-014 Scene Dependency Pack

- **SCN-014-D1 Pack format.** Decision: reuse FILE-001's `.pmscene` (version 1) and add an optional manifest field `slides` (`[{key, index, path}]`, index 1…20, path `assets/<key>-slide-<NN>.<ext>`), written only when non-empty; the file limit rises from 4 to 24. Rationale: the archive already maps every media reference to an archive-relative path with SHA-256 per file and passes PRE-014's entry-name rules; only slides were missing. Alternatives: a new pack format (duplicates FILE-001/002/003 code and checks); one slide record per distinct picture (saves bytes for repeated slides, but complicates order and remapping).
- **SCN-014-D2 Path audit.** Decision: `SceneArchivePathAudit` walks every JSON string (keys and values) of `manifest.json` and `scene.json` and flags `file:`, `~/`, `Containers/Data/Application`, and `/` followed by a system root (`var`, `private`, `Users`, `Library`, `System`, `Applications`, `tmp`, `Volumes`, `dev`, `etc`, `opt`, `usr`). The writer refuses (`absolutePath`) before writing. Rationale: catches a leaked store URL anywhere (also in unknown fields carried verbatim) without refusing ordinary text such as "1/2". Alternatives: refuse any string starting with `/` (would refuse a user's caption "/// drop"); scan only known fields (misses unknown content).
- **SCN-014-D3 Identifiers on import.** Decision: library imports give each media copy the identifier `derivedUUID("SCN-014|<role>|<index>|<sha256 of that media file in the pack>")` (FILE-004's derivation; role photo, slide, logo or video; index the slide position, 0 otherwise). Rationale: re-importing the same pack yields the same identifiers, FILE-008 keeps one payload, and the remapped scene is byte-identical, so FILE-004 reports it identical (no second scene or cue). Identifiers never collide with user-made ones (random v4) and differ by role, so a slide never shares an identifier with a photo or logo. Alternatives: random identifiers (re-import adds a "copy" scene every time); reuse any existing reference with the same payload (mixes roles; the current photo's reference would be released with it).
- **SCN-014-D4 Library import never makes media current.** Decision: adopt only. Rationale: a cue applies its scene's media when it is shown; importing must not change the output (SHOW-001-R6). The FILE-001 "make current" import stays for its own callers and gains slides.
- **SCN-014-D5 Order and rollback.** Decision: read and verify → plan (FILE-004, reads only) → stage every file in a staging folder → adopt (recording which identifiers were new) → install the scene (FILE-004, all or nothing) → on a refusal release only the new identifiers. Rationale: a failed import leaves the show and the stores as before.
- **SCN-014-D6 Entry points.** Decision: Scene Folders (scene row context menu, leading swipe, VoiceOver action; "Import Scene…" row in its actions section), not the switcher or the Show editor. Rationale: one place to learn, the smallest change in files other agents edit. The share sheet is `UIActivityViewController` (as user preset export); its completion removes the temporary file.
- **SCN-014-D7 File type.** Decision: declare `org.projectmios.scene-archive` (extension `pmscene`, conforms to `public.data`) in `UTExportedTypeDeclarations`; the picker accepts only that type. Rationale: FILE-001 already names the identifier; without the declaration the picker could not filter packs.
- **SCN-014-D8 UI test without the system picker.** Decision: DEBUG `-uitestScenePackFixture` seeds a scene with a photo, two slides and a logo, presents export results as a status line instead of the share sheet, and makes "Import Scene…" read the last exported pack instead of opening the picker. Rationale: the system share sheet and file picker run out of process and cannot be driven within the 30 s budget; the export → import path in the app is otherwise the shipping one.
- **SCN-014-D9 Byte-identical pictures (found while implementing).** Opaque pictures are stored as JPEG (MED-001), and re-encoding a JPEG on import changed its bytes (840 → 834 bytes in the acceptance test) and would lose quality on every export → import round. Decision: the pack import still runs the sanitizer (decoder checks, limits), and stores the pack's original bytes when they are the same image type and carry exactly the properties a fresh sanitized copy carries (container and image properties without the file size, same XMP); otherwise the sanitized copy (`ScenePackPicture`). A picture with location, camera or comment data therefore still loses it. The FILE-001 "make current" import is unchanged. Alternatives: a JPEG marker allow-list (ImageIO's own output already holds Exif and Photoshop blocks, so it cannot tell a clean copy from a photo with GPS data); lossless-only storage (changes MED-001).
- **SCN-014-D10 Re-import after a copy.** FILE-004 compares an incoming scene with the stored scene of the same ID only, so a pack first added as a copy would be added again as "copy 2". Decision: the preview also checks the copy's derived scene IDs (FILE-004-D2, first eight) for a stored scene equal to the pack's scene duplicated under that ID and name; then it reports the scene as already in the show.
