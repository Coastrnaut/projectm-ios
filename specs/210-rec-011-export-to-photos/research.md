# Research: REC-011 Export to Photos

- **REC-011-D1 Access level.** Decision: `PHAccessLevel.addOnly`. Rationale: least privilege; the app never needs to read. Alternatives: `.readWrite` (reads the library; rejected), the share sheet's own Save to Photos (iOS asks for add access too, but the app would get no outcome to report and no single place to keep the original safe; REC-012-R7 keeps it excluded).
- **REC-011-D2 When to ask.** Decision: read `authorizationStatus(for: .addOnly)` at the tap; only `.notDetermined` calls `requestAuthorization(for: .addOnly)`. Nothing is queried earlier. Rationale: constitution "permission at point of use".
- **REC-011-D3 Status mapping.** `.authorized`, `.limited` → granted; `.denied` → denied; `.restricted` → restricted; `.notDetermined` → notDetermined; unknown future values → denied (conservative, as the camera mapping).
- **REC-011-D4 Adding the item.** Decision: `PHPhotoLibrary.shared().performChanges { PHAssetCreationRequest.forAsset().addResource(...) }`; a still with `.photo` from its encoded bytes (PNG, HEIC or JPEG), a recording with `.video` from its file URL and `PHAssetResourceCreationOptions.shouldMoveFile = false` (the default, set explicitly), `originalFilename` the file's name. Rationale: no copy is made by the app; Photos copies the file; the original stays. Alternatives: `UIImageWriteToSavedPhotosAlbum` / `UISaveVideoAtPathToSavedPhotosAlbum` (re-encodes stills, selector callbacks, no add-only control; rejected).
- **REC-011-D5 Protecting the original during a save.** Decision: the coordinator records which item is saving (frame or the recording's URL); the panels and the library row disable Keep, Discard, Rename, Delete and Save to Photos for that item until the save ends. Rationale: Photos reads the file during `performChanges`.
- **REC-011-D6 Notices.** Texts in the contract; denied/restricted come from `PermissionCatalog.notice(.photosAdd, …)` so the catalog stays the single source (FILE-013 pattern), with Open Settings (iOS has a per-app Photos switch).
- **REC-011-D7 Announcements.** Decision: new ACC-011 row X8a `photosNotice` (capture lane, user-caused), posted from `CaptureEventChanges` when the coordinator's notice changes. The visualizer stays mounted under Settings, so the same post covers the Recordings screen.
- **REC-011-D8 Test seams.** Decision: protocols `PhotosAccessProviding` (status, request) and `PhotosSaving` (save image data, save video file), both injected into the coordinator; tests use recording fakes that count calls. DEBUG `-uitestPhotosAccess granted|denied|restricted|failing` installs the stand-in in the app. A live check on the simulator uses `xcrun simctl privacy <udid> grant|revoke photos-add org.projectmios.ProjectMiOS` (UI test gated by `TEST_RUNNER_REC011_LIVE_PHOTOS`).
- **REC-011-D9 Catalog check.** Decision: `check_permission_catalog.py` splits its forbidden list: `NSPhotoLibraryUsageDescription` stays forbidden anywhere in project.yml; `NSPhotoLibraryAddUsageDescription` is allowed in the app target only (it then must be in the catalog, which the existing key/catalog comparison enforces). Privacy manifest: Photos is not a required-reason API and nothing is collected, so `PrivacyInfo.xcprivacy` is unchanged (checked by `check_privacy_manifest.py`).
